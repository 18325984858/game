======================

IDA 数据库映射:
- libUE4.so      -> ida-pro-mcp-3
- libtersafe.so  -> ida-pro-mcp-4
- libtprt.so     -> ida-pro-mcp-5

结论摘要:

	libtersafe 承载检测策略和上报字段。
- #1/#2/#5/#9 在 libtersafe 有强字符串和引用证据。
- #3 GOT/PLT、#7 Java ClassLoader 缺少直接字符串证据, 只能标为“可能折叠在完整性/SDK JNI 逻辑中”。

1. maps 扫描: 周期 read /proc/self/maps, 匹配未签名/未在白名单的 .so 路径  ⚠️
--------------------------------------------------------------------------------
检测逻辑:
1) 打开 /proc/self/maps。
2) 逐行解析内存段: start-end, perms, path。
3) 抽取 path/basename, 对 .so 或可执行映射做白名单/签名/路径判断。
4) 命中未知模块路径时进入上报链; 是否本地 abort 取决于策略分支。

静态证据:
- libtersafe.so+0x564008: 字符串 "/proc/self/maps"。
- libtersafe.so+0x564028: 字符串 "/proc/self/maps"。
- libtersafe.so+0x321FBC: sub_321FBC 引用 maps 字符串, callgraph 显示调用 sub_4EE598 / sub_322E88 / sub_2F04CC。
- libtersafe.so+0x4E54BC: module 字符串处理函数, 引用字符串 "module" (libtersafe.so+0x986DA), callgraph 显示 getpid / memset / 多个格式化/采集 helper。
- 相关动态符号字符串: basename(libtersafe.so+0x32FD), strrchr(libtersafe.so+0x370A), strstr(libtersafe.so+0x36BD), strcasestr(libtersafe.so+0x3191), dladdr(libtersafe.so+0x341D), dl_iterate_phdr(libtersafe.so+0x39AC)。

模块偏移:
- libtersafe.so+0x321FBC  maps 初始化/读取入口候选
- libtersafe.so+0x564008  "/proc/self/maps" 字符串
- libtersafe.so+0x564028  "/proc/self/maps" 字符串
- libtersafe.so+0x4E54BC  module 上报/采集候选
- libtersafe.so+0x986DA   "module" 字符串

判定:
- 强确认存在 maps 扫描面。
- 从已有崩溃表现看它不是本次 SIGABRT/崩溃主因, 更像后台/服务端上报或辅助检测。


2. 代码段 CRC: 对关键 .text 段算哈希, 比对启动时基线, 检测 inline hook
--------------------------------------------------------------------------------
检测逻辑:
1) 枚举模块和 PT_LOAD 段, 找 r-x/.text 范围。
2) 对目标模块的代码段或指定函数窗口计算 CRC/hash。
3) 与启动基线或云端下发基线比较。
4) mismatch 进入 mrpcs_data_crc_error / hook opcode report 上报。

静态证据:
- libtersafe.so+0x9151E: 字符串 "%s;crc:%s"。
- libtersafe.so+0x9492C: 字符串 "mrpcs_data_crc_error"。
- libtersafe.so+0x3FD5C0: sub_3FD5C0 同时引用 "%s;crc:%s"、"mrpcs_data_crc_error"、inline hook/opcode 字符串, 是完整性/上报字段聚合入口候选。
- libtersafe.so+0x4E3D64: sub_4E3D64 引用 "module_size_in_range"; callgraph 显示它分派到多组 module/range helper, 符合枚举模块范围再计算/校验的结构。
- libtersafe.so+0x39AC: 动态符号字符串 "dl_iterate_phdr", 支持按 ELF program header 枚举模块段。

模块偏移:
- libtersafe.so+0x3FD5C0  CRC/inline hook 上报字段聚合入口候选
- libtersafe.so+0x9151E  "%s;crc:%s"
- libtersafe.so+0x9492C  "mrpcs_data_crc_error"
- libtersafe.so+0x4E3D64  module/range 校验候选
- libtersafe.so+0x97D86  "module_size_in_range"
- libtersafe.so+0x39AC   "dl_iterate_phdr"

判定:
- 强确认存在代码完整性/CRC 上报面。
- 若改写 libUE4.so/.text 或 Dobby inline patch 触碰被监控窗口, 会触发该面。


3. GOT/PLT 完整性: 检查 import 表项是否被改写 (PLT hook)
-----------------------------------------------------------
检测逻辑(推断):
1) 枚举目标模块 dynamic section / relocation 表。
2) 读取 GOT/PLT 目标地址。
3) 校验目标是否仍落在期望模块范围, 或与启动快照一致。
4) 失败后复用完整性上报链。

静态证据:
- 本轮未找到 "GOT" / "PLT" / "JUMP_SLOT" / "relocation" 等直接字符串。
- 可疑关联是 libtersafe.so+0x4E3D64 的 module/range 检查和 libtersafe.so+0x3FD5C0 的完整性上报聚合。
- libtersafe 导入/符号字符串中有 dladdr(libtersafe.so+0x341D) 和 dl_iterate_phdr(libtersafe.so+0x39AC), 足以支撑“地址归属模块校验”。

模块偏移:
- libtersafe.so+0x4E3D64  module/range 校验候选
- libtersafe.so+0x3FD5C0  完整性上报聚合候选
- libtersafe.so+0x341D   "dladdr"
- libtersafe.so+0x39AC   "dl_iterate_phdr"

判定:
- 弱确认。没有直接 GOT/PLT 字符串, 不能把它写成独立已确认实现。
- 更可能折叠在“模块地址归属 + CRC/完整性”通用策略内。


4. 栈回溯扫描: 周期 backtrace 当前/重点线程, 检查 LR/PC 是否落在白名单模块外  ✅ 主因
-----------------------------------------------------------------------------------------
检测逻辑:
1) 检测调度侧请求 unwind 信息。
2) libtprt 提供 unwind_xx_info_query / unwind_xx_ioctl 接口。
3) unwind 引擎读取线程上下文、栈、eh_frame/exidx, 展开 PC/LR 链。
4) 对每一帧 PC/LR 做 dladdr/模块归属判断。
5) 模块不在白名单或无法解释时进入本地 abort/kill 或上报链。

静态证据:
- libtprt.so+0xBA814: 导出 unwind_xx_info_query。
	反编译: 调 sub_1319D4() 获取全局表/管理器, 再调 sub_131C70(v6, a1, a2, a3) 查询 unwind 信息。
- libtprt.so+0xBAB9C: 导出 unwind_xx_ioctl。
	反编译: OLLVM 平坦化 switch, 对 cmd 1/2/4 分发到 sub_149040 / sub_148FFC / sub_128BF0 等。
- libtprt.so+0x131C70: 查询路径, 字符串 key 查表后把结果拷贝到调用方 buffer。
- libtprt.so+0x131DA4: 写入/更新 key-value 路径。
- libtprt.so+0x13E17C: 引用字符串 "unwind_xx_info_query", 用于导出名/接口名解析。
- libtprt.so 动态符号字符串: dladdr(libtprt.so+0x1CA6), ptrace(libtprt.so+0x1D1F), syscall(libtprt.so+0x1D42), pthread_create(libtprt.so+0x1B8A)。
- libtersafe.so 内也有 libunwind / _Unwind / .eh_frame 相关字符串, 但更像运行库/异常展开代码或策略侧复用。

模块偏移:
- libtprt.so+0xBA814   unwind_xx_info_query
- libtprt.so+0xBAB9C   unwind_xx_ioctl
- libtprt.so+0x1319D4  unwind 全局管理器 getter
- libtprt.so+0x131C70  unwind info query 查表/拷贝
- libtprt.so+0x131DA4  unwind info update/write
- libtprt.so+0x13E17C  "unwind_xx_info_query" 解析 helper
- libtprt.so+0x1CA6    "dladdr"
- libtprt.so+0x1D1F    "ptrace"
- libtprt.so+0x1D42    "syscall"

判定:
- 强确认, 并且最符合“我们死在这里”的现象。
- 只要采样到的任意帧 PC/LR 落在 libdobby.so、匿名 RX、Frida/Gum 等非白名单模块, 就可能触发本地终止。

模块偏移:

本次优先级判断
--------------
1) 触发本地崩溃的首要目标: #4 栈回溯扫描 (libtprt.so+0xBA814 / +0xBAB9C)。
2) 会影响 inline hook 稳定性的高风险项: #2 代码段 CRC 与 #5 inline trampoline opcode 检测 (libtersafe.so+0x3FD5C0 及相关字符串)。
3) 会影响注入/加载长期风险的项: #1 maps 与 #9 module 数量/范围检测 (libtersafe.so+0x321FBC / +0x4E3D64 / +0x4E54BC)。
4) #6/#8/#10 是环境/协议/调试辅助面; 目前证据偏“上报/策略”, 非本次本地崩溃主因。
